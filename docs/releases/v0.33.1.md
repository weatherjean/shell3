# v0.33.1 — reliable background supervision

This release makes long-running work easier to supervise and its outcomes harder
to lose. Background completions now enter automatic inbox-review turns, agents
can request one-shot progress checks, and workflow status distinguishes a live
execution owner from interrupted or expired work.

## Background work and inbox delivery

- `bash_bg` accepts `poll_in` from one minute to 24 hours in interactive console
  and Telegram sessions. The `shell3` tool can replace or cancel a check. Checks
  wait while a conversation is busy and survive command completion, but not host
  restart. One-shot mode rejects unsupported checks before launching work.
- Attached hosts automatically review `main` notices in batches of up to eight
  notices and 32 KiB of body text. Large bodies are delivered in UTF-8-safe chunks.
  Notices archive only after the exact delivered input is found in durable chat
  history. Failed or cancelled turns leave them pending; recovery may repeat a
  chunk rather than lose it.
- `/stop` pauses automatic inbox review and clears pending progress checks;
  `/superstop` also stops managed background commands. Ordinary user input resumes
  review. Successfully reviewed completions cancel redundant checks for that
  conversation. Ready console input takes priority over automatic turns.
  Telegram clears an emptied inbox's pending flag before releasing its turn slot.

## Process and provider reliability

- `wrk status` probes the execution lock and reports `execution_active`, persisted
  status, interruption/expiry, deadlines, recovery requirements, and exact attempt
  log paths. Files on disk alone are not treated as evidence of a live process.
- External runner helpers retain the execution lock and cancel their worker
  process group when the driver disappears. Closing a progress display pipe no
  longer interrupts durable workflow execution.
- Foreground attached tools reject `wrk run`, `wrk beat`, and `schedule run` before
  admission; use `bash_bg` for work that must leave the conversation available.
- Provider rounds stop after five minutes without model progress, including during
  connection setup and retries. Active reasoning/output extends the deadline;
  transport keepalives do not. Incomplete tool calls are not dispatched, and a
  timed-out request is not automatically replayed.

## Host feedback and scheduled failures

- Host actions show explicit names and outcomes. A bounded durable receipt journal
  and fresh host context distinguish a queued restart from a replacement host that
  actually initialized. Unreadable receipt history no longer prevents startup.
- Schedules can add `(notify-failure "main")` while retaining another `notify`
  destination for successful runs. Failed and cancelled runs use the override,
  including after restart or removal of the schedule declaration. The schedule
  ledger stays running while terminal-notice persistence needs retrying.
- A tested Python example demonstrates verified inserted/skipped application
  outcomes through existing workflow checks. A read-only retention inventory
  reports workflow history and pending notices; it has no deletion mode or default
  age policy. These helpers are in the source tree and require Python 3.9+.

## Upgrade notes

- Existing version-1 configuration and SQLite state remain supported; no database
  migration is introduced. Restart persistent hosts after replacing the binary.
  Changes to schedule declarations, including notification routes, require restart.
- Existing `main` backlog is now reviewed automatically and can cause model turns
  and Telegram replies after startup. The headless service does not review `main`.
- `silent` and `quiet` remain ordinary mailbox names, not discard policies. The
  failure override applies to newly admitted run snapshots; it does not reroute
  historical notices. Failures before a valid workflow snapshot exists remain in
  the schedule ledger and application log.
- Before downgrading, finish or cancel newer runs with the newer binary and restore
  compatible configuration. Older versions cannot parse `notify-failure` or all
  newer execution states. Preserve current conversation and application data.
- shell3 remains a process supervisor, not an OS sandbox. Progress checks are
  in-memory promises; durable schedules and inbox notices have separate lifetimes.

## Validation and release process

Release builds are gated by formatting/static analysis, race tests on Linux and
macOS, and deterministic local workflow/schedule acceptance. Release assembly
verifies dependencies instead of rewriting them. Archives are built for Linux and
macOS on amd64 and arm64, with SHA-256 checksums.

The release review started with all three unreleased implementation commits
after v0.32.1:

- `9a452d74`: long-running task supervision and host lifecycle feedback.
- `c4e03e60`: automatic inbox review and durable acknowledgment.
- `40d74793`: failure routing, verified outcomes, and retention inventory.

It also includes the console-priority and inbox-housekeeping fixes and the release
gates found during that review. The installer now refuses missing, mismatched, duplicate, or wrong-asset
checksums and requires a SHA-256 utility before extracting or installing a binary.
Installation-specific workflows and private deployment artifacts are not
part of this public release.

[Full comparison](https://github.com/weatherjean/shell3/compare/v0.32.1...v0.33.1)

The unpublished v0.33.0 candidate was superseded after artifact inspection found
a dirty source stamp caused by unignored build output. This release ignores that
output and verifies the embedded revision and clean source stamp.
